# Benchmark Plan

## 1. Instance generation

No existing benchmark combines curved lanes with heterogeneous, load-varying agents, so
instances are generated by this project (`src/benchmark/generate_instances.py`), following
CL-CBS's own methodology (Wen et al., 2022) for statistical comparability:

| Parameter        | Values                                                              |
|-------------------|----------------------------------------------------------------------|
| Map size          | small / medium / large lane networks (analogous to CL-CBS's 50x50, 100x100, 300x300 m) |
| Junction density  | low / medium / high (new axis vs. CL-CBS — this is where heterogeneous conflict cost concentrates) |
| Agent count       | 5-50 (lower ceiling than car-only CL-CBS since heterogeneous checking is more expensive) |
| Fleet mix         | 100:0, 50:50, 0:100 (forklift:quadruped)                             |
| Load condition    | laden / empty forklifts, toggled per instance                        |
| Instances/config  | 60 (matches CL-CBS for statistical power)                            |

## 2. Baselines

Implemented under `src/benchmark/baselines/`, in order of how much each isolates the
project's specific contribution:

1. **grid_cbs** — standard grid-discretized CBS. Expected to fail or produce paths that are
   not kinematically executable at junctions; establishes the cost of ignoring curvature
   entirely.
2. **cl_cbs** — forklift-only fleet, fixed curvature (no load dependence). Isolates the value
   of load-dependent curvature.
3. **hcbs** — heterogeneous fleet, fixed kinematics per class. Isolates the value of
   *changing* kinematics mid-mission.
4. **ours_no_load** — this project's solver with load-dependence switched off. Internal
   ablation control.
5. **ours_full** — this project's solver, full.

## 3. Metrics

Standard MAPF metrics, plus two specific to this project's contribution:

- Success rate, sum-of-costs, makespan, high-level node expansions, wall-clock runtime
  (standard, for comparability with CL-CBS/HCBS reported numbers).
- **Stability-margin utilization**: minimum realized stability margin along each forklift's
  executed path, and the fraction of instances where the load-dependent constraint is actually
  binding (vs. never active, which would undercut the motivation for modeling it).
- **Conflict-check overhead**: wall-clock cost of the junction swept-volume checks vs. the
  lane-segment interval-overlap checks, and both vs. the grid baseline's conflict-check cost.
  This is the main scalability risk and should be reported explicitly rather than folded into
  total runtime.

## 4. Physical-plausibility validation (subset)

For a small subset of instances (not the full benchmark sweep), validate executed trajectories
in a physics simulator rather than the algorithmic solver alone. Recommended: reuse
**MRP-Bench**'s pipeline (RMF traffic editor -> Gazebo world -> ROS2 orchestration) rather than
building a simulator from scratch — see `docs/related_work.md` for the reference. This checks
that solver output is actually trackable by a controller, which the algorithmic metrics above
cannot confirm on their own.

## 5. Reporting

Each baseline x configuration combination produces one CSV row per instance in
`results/<baseline>/<config>.csv` (schema in `src/benchmark/schema.py`). Aggregate plots
(success rate vs. agent count, runtime vs. junction density, etc.) are generated by
`src/benchmark/analyze.py` — not yet implemented, see module docstring for the planned
interface.
