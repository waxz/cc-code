# Benchmark Plan

## 1. Instance generation

No existing benchmark combines curved lanes with heterogeneous, load-varying agents, so
instances are generated by this project (`src/benchmark/generate_instances.py`), following
CL-CBS's own methodology (Wen et al., 2022) for statistical comparability:

| Parameter        | Values                                                              |
|-------------------|----------------------------------------------------------------------|
| Map size          | small / medium / large lane networks (analogous to CL-CBS's 50x50, 100x100, 300x300 m) |
| Junction density  | low / medium / high (new axis vs. CL-CBS — this is where heterogeneous conflict cost concentrates) |
| Agent count       | 5-50 (lower ceiling than car-only CL-CBS since heterogeneous checking is more expensive) |
| Fleet mix         | 100:0, 50:50, 0:100 (forklift:quadruped)                             |
| Load condition    | laden / empty forklifts, toggled per instance                        |
| Instances/config  | 60 (matches CL-CBS for statistical power)                            |

## 2. Baselines

Implemented under `src/baselines/` (`grid_cbs`) and `src/solver.py` (`ours_full`),
in order of how much each isolates the project's specific contribution:

1. **grid_cbs** — standard grid-discretized CBS. Expected to fail or produce paths that are
   not kinematically executable at junctions; establishes the cost of ignoring curvature
   entirely.
2. **cl_cbs** — forklift-only fleet, fixed curvature (no load dependence). Isolates the value
   of load-dependent curvature.
3. **hcbs** — heterogeneous fleet, fixed kinematics per class. Isolates the value of
   *changing* kinematics mid-mission.
4. **ours_no_load** — this project's solver with load-dependence switched off. Internal
   ablation control.
5. **ours_full** — this project's solver, full.

## 3. Metrics

Standard MAPF metrics, plus two specific to this project's contribution:

- Success rate, sum-of-costs, makespan, high-level node expansions, wall-clock runtime
  (standard, for comparability with CL-CBS/HCBS reported numbers).
- **Stability-margin utilization**: minimum realized stability margin along each forklift's
  executed path, and the fraction of instances where the load-dependent constraint is actually
  binding (vs. never active, which would undercut the motivation for modeling it).
- **Conflict-check overhead**: wall-clock cost of the junction swept-volume checks vs. the
  lane-segment interval-overlap checks, and both vs. the grid baseline's conflict-check cost.
  This is the main scalability risk and should be reported explicitly rather than folded into
  total runtime.

## 4. Physical-plausibility validation (subset)

For a small subset of instances (not the full benchmark sweep), validate executed trajectories
in a physics simulator rather than the algorithmic solver alone. Recommended: reuse
**MRP-Bench**'s pipeline (RMF traffic editor -> Gazebo world -> ROS2 orchestration) rather than
building a simulator from scratch — see `docs/related_work.md` for the reference. This checks
that solver output is actually trackable by a controller, which the algorithmic metrics above
cannot confirm on their own.

## 5. Reporting

`src/benchmark/run_solver_benchmark.py` runs `ours_full` and `grid_cbs` on the same
generated instances and writes one flat CSV (columns: instance_id, map_size,
junction_density, n_agents, fleet_mix, solver, success, sum_of_costs, makespan,
runtime_s, high_level_expansions, min_stability_margin), plus a printed
success-rate/runtime/cost summary per solver. `benchmark.sh` runs a small,
CI-runtime-bounded sweep of this and commits both the CSV and a text summary into
`results/`. This is simpler than the originally-planned per-baseline-file schema
below it replaces; extending to `cl_cbs`/`hcbs`/`ours_no_load` as additional
`solver` values in the same CSV is the natural way to grow it rather than
introducing a new schema.

## 6. Current status vs. this plan (updated after implementing the solver)

What's implemented and real, not planned:
- `grid_cbs` baseline: implemented, independently verified (`tests/test_grid_cbs.py`)
  against hand-built swap-conflict cases.
- `ours_full`: implemented as `src/solver.py`, using route-selection low-level
  planners (see scope notes in `src/planners/forklift_planner.py`) rather than raw
  continuous-space Reeds-Shepp curve generation.
- `src/benchmark/run_solver_benchmark.py` runs both on the same generated instances
  and reports the metrics in section 3 above.

What's not yet implemented: `cl_cbs` and `hcbs` as literal baselines (a real
reimplementation of those papers' specific algorithms, as opposed to the classical
grid-CBS baseline actually built here), and the `ours_no_load` ablation as a
separate configurable run (the load-dependence can currently only be disabled by
editing `ForkliftKinematicProfile` directly, not via a CLI flag).

### Known limitation: incompleteness on sparse, dense-conflict instances

Running the comparison (not just designing it) surfaced a real completeness gap in
`ours_full`: on a sparse lane-graph (few alternate routes between junctions) with
3+ agents contesting the same segment, the solver can fail to find a solution that
likely exists, because the low-level planners fix their route via Dijkstra once and
only insert waits under a high-level constraint -- they never try an alternate route
around a contested segment. This was confirmed, not assumed: tracing a specific
non-converging instance showed the high-level search exploring hundreds of branches
that all plateau at the exact same total cost, which is the signature of a genuine
incompleteness rather than an expansion-budget shortfall (re-running the same
instance at 5000 expansions instead of 300 made no difference).

The fix is to make the low-level planner's response to a constraint be "temporarily
remove this edge and re-run Dijkstra" rather than "keep the same path, just wait" --
this is the clear next implementation step, tracked here rather than worked around
by tuning the benchmark's instance sizes until failures stopped showing up.

Separately, the `grid_cbs` baseline shows its own, unrelated limitation: the
grid-discretization translation (`instance_to_grid` in
`src/baselines/grid_cbs.py`) can snap multiple distinct lane-graph junctions onto
the same coarse grid cell on a small map, which can make an otherwise-solvable
instance spuriously harder after translation. This is a property of the
map-translation step, not a bug in the grid-CBS algorithm itself.
